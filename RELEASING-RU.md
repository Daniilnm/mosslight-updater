## Как выпустить следующую игровую версию

1. Проверить Git status и действующее поручение пользователя. Подготовка выпуска не разрешает менять работающий сервер. Сначала изменить главные KubeJS/генератор квестов/apply_configs.py/исходники модов по AGENTS.md. Установку и перезапуск выполнять только по актуальному разрешению, с бэкапом и проверкой игроков, если это условие пользователя. Тестовый и основной одновременно не запускать.
2. Убедиться, что клиентские JAR и нужные конфиги соответствуют новому выпуску. `pack_friends.py` читает моды и конфиги **из клиента**, KubeJS из `BMC5-tools/kjs`, квесты **из основного сервера**. Если новая версия пока только в pending, этот скрипт соберёт старые установленные файлы. Нельзя выдавать их за новую версию. Для такого случая собрать проверенный отдельный staging ZIP или дождаться разрешённой установки; живые папки ради упаковки не менять.
3. Выбрать новый номер, например v22. Никогда не перезаписывать v21 или его опубликованные объекты. Сверить содержимое архива, отсутствие двух версий одного мода и личных файлов. При чтении квестов работающего сервера убедиться, что файлы не менялись во время упаковки; если менялись, повторить получение согласованной копии без остановки по собственной инициативе.

```powershell
Set-Location 'D:/Games/Minecraft/BMC5-tools'
python -I ./pack_friends.py BMC5-mods-2026-10-16-v22.zip
```

Дата и номер здесь и далее — пример: подставить фактические, проверить, что выходного ZIP ещё нет. Скрипт пишет в Downloads текущего пользователя. Полный архив оставить для первой установки и восстановления сторонних модов, не загружать весь ZIP на публичный GitHub без проверки прав на содержимое.

4. Перейти в `mosslight-updater`. Проверить подпись предыдущего `pack.json`, сохранить все исторические Releases. Передать `previousPack` **локальным путём** к последнему подписанному каталогу: это сохраняет ссылки на старые неизменившиеся объекты и список устаревших файлов даже при пропуске версий. Старые архивы v17–v21 также полезно сохранить.
5. Новый собственный JAR внести по точному SHA-256 в `approved-jars.json`. Сторонние JAR без разрешения не добавлять туда автоматически. Их хеши входят в каталог, но сами файлы не зеркалируются. Если появился новый сторонний JAR, сборщик намеренно остановится; сначала решить разрешённый способ доставки. Не обходить проверку и не обещать обновление в один клик, если новый файл ещё не доступен законным способом.

### Обычный выпуск: меняется только сборка

Для v22 сохранить приложение **1.0.0 без пересборки**. `build-release.ps1` всегда пересобирает EXE: его нельзя запускать с прежним номером приложения ради одного изменения сборки. Использовать ReleaseTool build с исходным опубликованным EXE. Пример из PowerShell 7 / Windows PowerShell:

```powershell
Set-Location 'D:/Games/Minecraft/BMC5-tools/mosslight-updater'
dotnet restore ReleaseTool/Mosslight.Update.ReleaseTool.csproj --configfile NuGet.Config
if ($LASTEXITCODE -ne 0) { throw 'Restore failed' }
$releaseConfig = @{
  repository = 'Daniilnm/mosslight-updater'
  privateKey = "$PWD/.private/release-private.pem"
  archive = 'C:/Users/Даня/Downloads/BMC5-mods-2026-10-16-v22.zip'
  executable = "$PWD/artifacts/published-v21/app-v1.0.0/Mosslight.Update.exe"
  output = "$PWD/artifacts/release-v22"
  packVersion = 22
  appVersion = '1.0.0'
  notes = @('Кратко описать фактические изменения для друзей.')
  previousPack = "$PWD/artifacts/published-v21/pack-v21/pack.json"
  legacyArchives = @(Get-ChildItem -LiteralPath 'C:/Users/Даня/Downloads' -Filter 'BMC5-mods-*-v*.zip' | Select-Object -ExpandProperty FullName)
  approvedJarHashes = @(Get-Content approved-jars.json -Raw | ConvertFrom-Json)
}
if (Test-Path -LiteralPath $releaseConfig.output) { throw 'Нужна новая пустая папка выпуска' }
$configPath = "$PWD/.private/release-v22.json"
[IO.File]::WriteAllText($configPath, ($releaseConfig | ConvertTo-Json -Depth 10), [Text.UTF8Encoding]::new($false))
dotnet run --project ReleaseTool/Mosslight.Update.ReleaseTool.csproj --no-restore -- build $configPath
if ($LASTEXITCODE -ne 0) { throw 'Build failed' }
dotnet run --project ReleaseTool/Mosslight.Update.ReleaseTool.csproj --no-restore -- validate artifacts/release-v22 Daniilnm/mosslight-updater .private/release-public.pem
if ($LASTEXITCODE -ne 0) { throw 'Validation failed' }
```

Проверить SHA-256 полученных `app-v1.0.0/Mosslight.Update.exe` **и `app.json`** относительно опубликованных. Подпись RSA используется детерминированная; при тех же данных `app.json` должен совпасть. Отличие — причина остановиться, а не заменить вложение старого выпуска. В папке нового pack будут только новые gzip-объекты и полный подписанный каталог.

### Если меняется сам обновлятор

Изменить код, выполнить тесты, назначить новый `AppVersion`, например 1.0.1. Тот же ключ и репозиторий сохраняются. После этого допустим `build-release.ps1` с **новым номером приложения**, новым/нужным номером сборки и отдельным Output:

```powershell
./build-release.ps1 -Repository 'Daniilnm/mosslight-updater' -PrivateKey '.private/release-private.pem' -Archive 'C:/Users/Даня/Downloads/BMC5-mods-2026-10-16-v22.zip' -LegacyArchiveFolder 'C:/Users/Даня/Downloads' -PackVersion 22 -AppVersion '1.0.1' -PreviousPack 'artifacts/published-v21/pack-v21/pack.json' -Output 'artifacts/release-v22-app101' -Notes @('Фактические изменения сборки и программы.')
if ($LASTEXITCODE -ne 0) { throw 'Build failed' }
```

Если нужно выпустить только приложение без новой сборки: создать новый `app-v1.0.1`, но использовать **точные прежние** файлы `pack-v21`, и подписать канал с `PackVersion=21 / AppVersion=1.0.1`. Текущий build всегда создаёт оба описания; при таком сценарии контролировать полное совпадение всех файлов существующего pack перед публикацией. Не пересоздавать уже опубликованный pack с изменёнными notes/legacyPaths под тем же номером. При сомнении проще выпустить новую пару v22/1.0.1.

Друзья получат кнопку «Обновить программу». Помощник проверяет подпись и SHA, сохраняет предыдущий EXE, заменяет программу и ждёт подтверждения открытия окна; неудача возвращает предыдущий EXE. Пользователь вручную заново скачивать приложение не должен, пока ключ доверия и схема совместимы. Смену ключа/репозитория нужно проектировать отдельно; простой выпуск с новым ключом старые EXE не примут.

## Публикация в GitHub Releases

Сначала проверить подготовленные файлы и разрешение пользователя на публикацию данного выпуска. Подключённый GitHub-коннектор использовать для исходников и чтения состояния. В этой сессии создание репозитория и загрузка вложений Releases были доступны только через браузер. Коннектор не выдаёт локальному CLI токен, не искать его в браузере или файлах авторизации.

Если владелец отдельно настроил `GH_TOKEN` в окружении с Contents:write только для репозитория, имеется готовый издатель:

```powershell
dotnet run --project ReleaseTool/Mosslight.Update.ReleaseTool.csproj --no-restore -- publish artifacts/release-v22 Daniilnm/mosslight-updater .private/release-public.pem
if ($LASTEXITCODE -ne 0) { throw 'Publication failed; check remote state before retry' }
```

Без токена загрузить в браузере те же подготовленные файлы. Порядок:

1. Создать draft `pack-v22`, загрузить **все** файлы из локального `pack-v22`, дождаться конца загрузки и проверить имена, размеры и digest. Опубликовать pack.
2. Если приложение новое, так же опубликовать `app-v1.0.1` с EXE и `app.json`. При неизменной 1.0.0 ничего в её выпуске не заменять.
3. Проверить, что все URL нового каталога, включая объекты старых Releases, доступны анонимно. Файлы версионных выпусков неизменяемые; при несовпадении хеша остановиться и выяснить причину.
4. **В последнюю очередь** заменить только `stable/channel.json` на подготовленный и проверить подпись. Этот выпуск должен оставаться изменяемым; immutable release для stable не включать. Частичная публикация до переключения stable не должна отправлять друзей на незавершённую версию.
5. Оставить Latest на выпуске приложения, чтобы открывший страницу сразу видел EXE. CLI publisher при создании stable может назначить Latest ему — проверить и при необходимости исправить через страницу Releases. Работа приложения использует тег stable и не зависит от бейджа Latest.
6. Сохранить новую полную папку артефактов как `artifacts/published-v22`, журнал проверки и SHA; сделать Git-коммит исходников/документов, не включая ключи, кэш, ZIP, bin/obj. В `BMC5-следующая-сессия.md` и `BMC5-план.md` записать точные текущие теги, изменения, проверки, бэкап, состояние серверов и непроверенное в игре. Обновить эту инструкцию для новой базы.

**Старые pack/app Releases не удалять.** Последний каталог может ссылаться на их объекты; удаление ломает пропуск версий, восстановление и проверку файлов. Полные исторические архивы не являются заменой сохранённых публичных объектов.

## Откат и неполадки

- У друга: закрыть игру, настройки Mosslight → «Откатить последнее обновление». Состояние лежит в `.mosslight` выбранного клиента, хранятся три завершённых бэкапа; более поздние личные изменения защищаются отдельно. После аварийного закрытия сначала дать приложению восстановить журнал. Не удалять `.mosslight` ради устранения ошибки.
- Ошибка сети: повторить; есть докачка и проверка SHA. Отсутствующий сторонний JAR: «Указать полный архив» нужной версии; файл извлекается только при совпадении хеша. Оригинальный ZIP поверх клиента не распаковывать.
- Неизвестный Java-процесс/ошибка CIM: обновление блокируется, процесс не завершается. Не отключать защиту ради теста живого клиента; выяснить причину или попросить владельца закрыть игру самостоятельно.
- Плохой опубликованный выпуск: остановить дальнейшее распространение, при необходимости вернуть сохранённый подписанный `stable/channel.json` на прежний выпуск. **Это не откат уже обновлённых клиентов.** Друзьям нужен ручной откат или исправленный выпуск с новым номером; сервер должен быть с ними совместим. Не менять файлы уже опубликованных тегов.
